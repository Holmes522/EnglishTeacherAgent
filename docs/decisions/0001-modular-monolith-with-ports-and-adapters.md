# ADR-001：以模块化单体和端口/适配器启动

## 状态

Proposed

## 日期

2026-09-09

## 背景

产品要快速完成文本 MVP，同时未来可能更换词典、模型、语音供应商，增加语言包与界面插件。当前团队规模、流量和独立扩容边界未知。

## 决策

采用 TypeScript monorepo 和模块化单体。领域核心只依赖供应商无关的端口；Next.js Web/BFF 与异步 Worker 可独立进程部署，共享契约和领域包。出现明确的独立扩容、数据主权或发布节奏需求后，才按模块边界拆服务。

## 备选方案

### 一开始使用微服务

- 优点：独立部署与扩容边界清晰。
- 缺点：在边界尚未验证时增加网络失败、分布式追踪、契约和部署成本。
- 未选原因：当前收益不足以覆盖复杂度。

### 单个 Next.js 应用内直接调用所有供应商

- 优点：代码最少、原型快。
- 缺点：业务与框架/供应商耦合，后台批量恢复困难，后续拆分代价高。
- 未选原因：不能满足批量可靠性和供应商可替换要求。

## 后果

- 前期部署和本地开发更简单。
- 必须通过依赖规则和契约测试防止“模块化”退化成任意跨包调用。
- 数据库暂可共享，但模块只能通过所属 repository/应用服务访问其表。
